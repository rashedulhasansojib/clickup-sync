1 · v2 in one page — the four problems it solves

v1 (Phases 0–3 of the 2026-06-27 integration plan) shipped the engine: shared cookie-session auth, ClickUp write-back, RAG knowledge base, smart-assign + a learning loop. Every task on a run carried three predictions (sprint / duplicate / owner) and a nudge chip when the learning gate fired. But four things blocked trust and adoption — and v2 (the 2026-07-18 plan) is the cockpit rebuild that fixes them.

Problem 1 · The review page does everything

apps/meetsy-web/app/runs/[runId]/* was ~1200 lines rendering stepper + tasks + push editor + chat + learning in one scroll. No home, no history, no way back to a past run except URL memory.

v2 fix → Phase 1 introduces /home, /meetings, full-text search, tabbed /runs/:id (Overview / Push / Chat / Insights).

Problem 2 · Evidence is computed but not shown

assignment.ranked[], evidenceTaskIds (5 precedent tasks per candidate), FieldPrediction.candidates[], kbContext.sourceId — all in the payload, none rendered. Every task-id chip was dead text.

v2 fix → Phase 2 rewrites signals.tsx so evidence is expanded by default; every chip is a clickable button that opens a side sheet with the ClickUp task's title/status/owner/URL.

Problem 3 · The learning loop is invisible until it fires

The panel at components.tsx:1021 filtered gatePassed===true and dropped the tail. Users couldn't see a pattern building up (2/3 corrections in). Metric labels used jargon ("Raw model accuracy proxy").

v2 fix → Phase 3 adds /learning (Active / Building up / Coverage), an SSE near-gate toast, FIELDS = ["assignee","sprint"] expansion, plain-English metric labels.

Problem 4 · The KB is legible only during onboarding

GET /workspaces/:id/kb/search (hybrid RRF) and /kb/documents/:docId existed with no UI. Nothing to browse or inspect what the model knows about your workspace.

v2 fix → Phase 4 consolidates everything under /kb — Overview / Tasks / Documents / Search / Rebuild — plus a global ⌘K palette that searches the KB from any route.

Plus a silent-loss bug (Phase 0 R1/R2): AnalysisRun.result's five signal keys (kbContext, fieldPredictions, duplicates, assignment, adjustments) were stripped by analysis.service.ts:227 on every feedback submit and every chat-added task — so a run's evidence disappeared the first time it was touched. v2 Phase 0 introduces ReviewResultSchema in @ma/shared + a mergeSignals() helper called before every persist. All five keys (plus the new neighboursByTask from Phase 2) now round-trip.

What a v2 user gets, in one sentence

Land on /home after login → see recent runs and a personal "is-the-model-getting-better-at-predicting-me" digest → open any past run without URL memory → see evidence expanded on the task cards → click any chip to see the actual ClickUp task → watch the learning loop build up instead of just firing → tune per-workspace thresholds with preview replay → and drive it all keyboard-first, dark-mode-aware, on any screen size.

2 · Audience decision + the six phases

The single locked audience decision for v2, made 2026-07-18 with the product owner: IC engineers checking their assignments. Every downstream choice follows from it.

What "IC engineers as primary user" changed:
  • Evidence panels default to expanded, not collapsed — an IC wants to see the reasoning without an extra click.
  • Every provenance chip (CU-01H…) is clickable → side sheet with title/owner/status/link.
  • Review page gets keyboard traversal (j/k between tasks, Esc closes the sheet).
  • Push editor becomes a secondary tab, not the default view. Overview leads.
  • Nudges are framed as "here's what your team taught the model", not "click accept to be faster."

3 · System architecture & the dependency graph

Meetsy is a separately-deployable sibling to Clicksy. Shared: login/session, org/workspace model, one Postgres (Meetsy owns meetsy schema, reads Clicksy's public read-only), one ClickUp token, one Redis instance. Meetsy adds an Azure OpenAI dependency for the pipeline (chat + embeddings on the unified niftyaibd-resource.services.ai.azure.com/openai/v1 endpoint as of 2026-06-29).

What DID and DIDN'T change under the hood

Changed (v2)
  • Result-persist path rewired to preserve five signal keys + neighboursByTask.
  • Two new meetsy tables (WorkspaceMlConfig, AnalysisRunSnapshot) + a dead-letter table + a tsvector column on Meeting.
  • Web routing collapsed: / → /home, /onboarding → /kb, /settings/kb → /kb?tab=rebuild.
  • Learning gate constants (MIN_CORRECTIONS, MIN_AGREEMENT) sourced from WorkspaceMlConfig; duplicate bands too.
  • SSE learning-stream via Redis pub/sub, mounted at the shell.
Deliberately did NOT change
  • The engine itself. Same pipeline, same retrieval, same smart-assign math from v1 Phase 3.
  • Clicksy's src/. All Clicksy-side edits (v1) were the two cookie-Domain lines.
  • Session shape. Same clickup_sync_sid cookie, same CSRF double-submit.
  • Model choice — gpt-5.5 stays the pipeline main; overrides land in WorkspaceMlConfig.models but are stored, not yet consumed (deferred).

4 · Phase 0 — Foundations

Goal: unblock every subsequent phase in one PR triple. Shipped as PR-A (signal-loss fix), PR-B (Prisma models + endpoints), PR-C (design-system foundations).

PR-A · signal-loss fix

Root cause (grounded in v2 spec §1.1): loadRunContext at analysis.service.ts:227 parsed run.result with strict AnalysisResultSchema.parse(), dropping the five signal keys. assemble() then rebuilt a strict AnalysisResult without them. Both feedback and chat writes persisted the stripped payload. As a knock-on, push.service.ts:158 read .fieldPredictions off the raw JSON blob and returned {} — the FieldOverride logger silently died for those runs.

Fix:

  • New packages/shared/src/review-result.ts — Zod source-of-truth for KbContextHitSchema, TaskPredictionSchema (with FieldPredictionSchema, PriorCandidateSchema, DuePredictionSchema), DuplicateHitSchema, TaskAssignmentSchema, TaskAdjustmentsSchema. Every signal key is optional so historical runs still parse.
  • ReviewResultSchema re-exported and swapped into RunResponseSchema.result, SubmitFeedbackResponseSchema.result, SendChatResponseSchema.result.
  • New mergeSignals(base, source) helper called from both write paths (submitFeedback line 291, sendChat line 366) — the merged ReviewResult, not the stripped AnalysisResult, is what gets persisted and returned.
  • Web: local ReviewResult interface in signals.tsx (77 lines) deleted; now imports from @ma/shared.

PR-B · Prisma models + endpoints

erDiagram WorkspaceMlConfig { string workspaceId PK string orgId json tunables json models string updatedBy datetime updatedAt datetime createdAt } AnalysisRunSnapshot { string runId PK string workspaceId json tunables json models datetime createdAt } AnalysisRun { string id PK string workspaceId string status json result datetime createdAt } AnalysisRun ||--o| AnalysisRunSnapshot : "1:0..1 cascade"
  • New model WorkspaceMlConfig — workspaceId PK (one row per workspace), tunables JSONB, models JSONB, updatedBy?, index on orgId. Soft ref to public.workspaces.
  • New model AnalysisRunSnapshot — 1:1 with AnalysisRun via cascade FK, frozen tunables+models. Append-only. Enables reproducible /tuning preview in Phase 5.
  • New index on AnalysisRun(workspaceId, createdAt) — powers the newest-first paginated runs-list.
  • New GET /workspaces/:id/clickup/tasks/:taskId — resolves ClickUp task ids surfaced in duplicate chips + evidenceTaskIds to {title, status, assigneeName, url}. Soft-scopes by workspace; returns null on soft-deleted tasks so the chip degrades to "unavailable."
  • New GET /workspaces/:id/runs?limit&offset&status — paginated list with a derived pushStatus: not_configured / not_pushed / partial / pushed. Batches one $transaction([findMany,count]) plus a page-wide TaskPush.findMany.

PR-C · design-system foundations

Adds shadcn/ui + Radix primitives + lucide-react + next-themes + sonner to apps/meetsy-web. Sixteen primitives installed (button/card/dialog/sheet/tabs/dropdown-menu/command/tooltip/skeleton/sonner/input/select/label/checkbox/radio-group/separator). Existing app/ui.tsx becomes a one-line shim that re-exports from app/ui-legacy.tsx so no caller migration is forced — later phases opt in.

6 · Phase 2 — Evidence-first review + push retry

Goal: make the review page the answer to "why did the pipeline think that?" — every signal the API computes is rendered inline, expanded by default, with drill-down. Shipped as PR-H (kNN neighbours), PR-I (push retry queue + dead-letter), PR-J (evidence panels), PR-K (chip → side-sheet + retry-failed button).

PR-H · top-5 kNN neighbours attached to run.result

The kNN neighbours per task were already computed by FieldPredictionService and threaded through the processor for owner ranking — then dropped on the floor at persist. PR-H adds neighboursByTask so the review UI can show "why did the pipeline think of this task as similar?" without re-embedding.

  • Shared schema: NeighbourHitSchema in @ma/shared — mirrors the runtime Neighbour interface with createdDate/closedDate as z.string().datetime().nullable().
  • Persist: the result: {...} write at analysis.processor.ts:243 gains neighboursByTask: sliceNeighbours(taskAnalysis.neighboursByTask, 5).
  • mergeSignals(): extended to preserve neighboursByTask — same failure mode Phase 0 R2 fixed for the other signal keys.
  • Bounds: top-5 × ~20 tasks × ~100 bytes ≈ 10 KB/run — trivial vs. transcript-sized fields already on run.result.

PR-I · push retry queue + dead-letter

sequenceDiagram participant U as User participant W as meetsy-web participant A as PushRetryController participant Q as meetsy-push-retry (BullMQ) participant P as PushRetryProcessor participant DB as Postgres participant CU as ClickUp U->>W: click "Retry failed (N)" W->>A: POST /runs/:id/push/retry { taskIds? } A->>DB: find failed TaskPush rows A->>Q: enqueue N jobs (attempts: 4, exp backoff) A-->>W: { enqueued: [], skipped: [] } loop for each job Q->>P: process job P->>DB: read TaskPush by (runId, taskId) alt already pushed P->>P: no-op else P->>CU: replay stored payload alt success P->>DB: TaskPush(status="pushed", ...) else final failure P->>DB: write PushDeadLetter row P->>DB: TaskPush.status stays "failed" end end end
  • Hand-authored migration adds meetsy."PushDeadLetter" table with {id, runId, meetsyTaskId, workspaceId, jobId, payload, errorMessage, errorStack, attemptsMade, failedAt, retriedAt, resolvedAt, resolvedBy} + 2 indexes.
  • Queue name meetsy-push-retry. Job id ${runId}:${meetsyTaskId}:${nonce} (nonce is Date.now().toString(36) — per-enqueue so a retry-after-retry actually runs; the DB row is the idempotency key). Options: attempts: 4, backoff: { type: "exponential", delay: 2000 }.
  • Retry endpoint POST /runs/:id/push/retry — body { taskIds?: string[] }. Response { enqueued: [], skipped: [{ meetsyTaskId, reason }] }. Reasons: not_found, not_failed:<status>, enqueue_failed:<msg>.
  • Dead-letter admin PushDeadLetterController at /workspaces/:id/push/dead-letter — Owner/Admin only; GET lists unresolved by default, POST /:deadLetterId/resolve hand-marks with resolvedBy = user.userId.

PR-J · evidence panels expanded by default

signals.tsx rewritten from the ground up. The old file rendered four shallow rows (duplicates → 3 pred chips → optional nudge → owner name-only) with assignment.ranked[], FieldPrediction.candidates[], and evidenceTaskIds never rendered.

Sections rendered per task card (each short-circuits when its signal is absent):

  1. Duplicates — every d.taskId renders as a TaskChip (red/amber by band).
  2. Suggested fields — Sprint / Due / Estimate chips PLUS a sub-strip of sim-weighted candidates (from A · 42% · B · 25% …), picked value styled distinct. A clamp badge appears when isModal === false (LLM overrode the modal top).
  3. Owner — top-3 ranked candidates with score bars (ownershipScore), closed/open/tracked-hours line, plus every evidenceTaskIds (up to 5) as clickable TaskChips. "Show N more" expands to the full ranking; recommended candidate highlighted green.
  4. Learning nudge — assignee AND sprint (Phase 3 fills the sprint side of TaskAdjustments).
  5. Similar (neighboursByTask) — top-3 neighbours as TaskChips with the cosine %.

PR-K · clickable chips → side sheet + retry-failed button

  • TaskSheetProvider — a single side-sheet slot per view; any chip in the subtree calls openTaskSheet(taskId). Scoped to runs/[runId]/page.tsx in Phase 2; hoisted to AppShell in Phase 4 so the KB tab can reuse it.
  • TaskChip — a real <button>, 6 tone variants, focus ring for keyboard traversal. Falls back to a no-op when no provider is mounted.
  • TaskDetailSheet — right-side Sheet, re-fetches on each open via api.getClickupTask(workspaceId, taskId). Three legit states: loading, loaded (title/status/assignee/updatedAt/"Open in ClickUp ↗"), null (task predates KB — legitimate; message reassures the chip is still trustworthy).

7 · Phase 3 — Learning trust

Goal: make the loop legible and trustable. Before Phase 3 the loop's state was hidden in a single settings panel; users saw a nudge or didn't, with no signal that they were "one correction away" from teaching the loop. Shipped as PR-L (FIELDS expansion), PR-M (Redis cache + gate + history), PR-N (near-gate SSE), PR-O (/learning page).

PR-L · FIELDS = ["assignee", "sprint"]

What "expand the learning loop" means concretely: before v2, LearningService was hardcoded to one field. Snapshot type was {assignee: FieldAggregate}, TaskAdjustments was {assignee?: …}, push only branched on the assignee prediction. Phase 3 widens to a second learnable field (sprint) with the discipline that adding a THIRD field in a future phase is a five-line change.
  • CorrectionStat gains field: string (which learnable field) and key: string (URL-safe base64url of field|predicted|confirmed, used as the path segment on /learning/patterns/:key/history).
  • Sprint resolution asymmetry (documented): assignee resolves clickupUserId → name, sprint resolves via WorkspacePushConfig.sprintLists[] (listId → name). Both happen at aggregate time.
  • Existing spec suite ported — every aggregateField(...) call now passes "assignee" first arg. New learning.service.sprint.spec.ts proves the sprint path end-to-end.

PR-M · Redis snapshot cache + gate endpoint + pattern history

  • LearningCacheService — Redis KV cache for LearningService.snapshot(). Key meetsy:learning:snapshot:v1:{workspaceId}, SETEX 3600. Hard-invalidated on logFieldOverride. The v1 guards against a future snapshot-shape change reading a stale value. Read-through-cached: hit returns stored value; miss falls through to DB scan then writes back.
  • GET /workspaces/:id/learning/gate — returns {minCorrections, minAgreement, nearGateThreshold, fields}. Workspace-independent today; Phase 5 makes it per-workspace by reading from WorkspaceMlConfig (shape stays stable).
  • GET /workspaces/:id/learning/patterns/:key/history — decodes the base64url key (400 malformed / unknown field), consults the resolved snapshot for stats (404 if the pattern isn't in the workspace), then scans up to 500 newest FieldOverride rows and filters to those matching (predicted, confirmed). nudgeShown per entry so the UI can badge nudge-influenced rows.

PR-N · near-gate SSE toast

  • Coverage — per-field: predictions seen, "Predictions you changed" (formerly rawOverrideRate), "Suggestions shown" (nudgeSample), "Suggestions accepted", and — when > 0 — Unresolved (amber, so a resolution bug looks like a resolution bug, not "sparse data").

8 · Phase 4 — /kb consolidation

Goal: replace the seven-step /onboarding wizard and the deeply-buried /settings/kb with a single canonical /kb route, plus a global ⌘K palette so KB search reaches the user from anywhere. Shipped as PR-P (GET /kb/tasks), PR-Q (/kb shell + 5 tabs), PR-R (retire /onboarding), PR-S (⌘K palette).

PR-P · GET /workspaces/:id/kb/tasks

  • KbTasksService joins KbChunk (meetsy) with public.clickup_tasks and returns the distinct set of embedded ClickUp tasks, keyset-paged on (updated_date DESC NULLS LAST, task_id DESC).
  • ?filter=<q> narrows via a case-insensitive ILIKE against task_name, client, and assignees_names.
  • Cursor is base64url(JSON.stringify({u: iso|null, t: taskId})) — malformed → 400.
  • Runs via prisma.$queryRaw — Prisma's groupBy doesn't compose keyset paging + a distinct chunk count in one round-trip; all params bound through the tagged template.

Signal keys on AnalysisRun.result

  • kbContext — the ranked KB hits used at prompt time (workspace-level grounding).
  • fieldPredictions — per-task {sprint, due, estimate}: modal value + sim-weighted candidates + priors.
  • duplicates — per-task list of {taskId, sim, band} at the flag/suggest thresholds.
  • assignment — per-task {recommended, ranked[], reasoning} with per-candidate {ownershipScore, evidenceTaskIds}.
  • adjustments — per-task {assignee?, sprint?} — the "learning nudge" pulled from LearningService.snapshot().
  • neighboursByTask — new in Phase 2 — top-5 kNN neighbours per task from FieldPredictionService. Cosine-descending, ~10 KB/run.
Round-trip invariant. All six signal keys survive submitFeedback and sendChat mutations via mergeSignals(assembled, ctx.result). Historical runs (pre-v2 Phase 0) keep working: every key is optional on ReviewResultSchema, so a legacy result with none of them parses cleanly.
